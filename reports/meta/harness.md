# ハーネスは分析の質を上げるか — Geo-Voyager v0.1.0 との比較 (2026-10-13)

hfu の仮説: **適切なハーネスが高いレベルの分析を生む。** その観点から、[yuiseki/Geo-Voyager v0.1.0](https://github.com/yuiseki/Geo-Voyager/tree/v0.1.0)
の方針と実装が、この北海道測量概況の作業 (D16〜D33) の参考になるかを分析した。

## 1. Geo-Voyager は何をしているか

ローカル LLM (文脈 8,192 トークン) が地理の問いを自分で立て (curriculum)、小さな調査 (Intent) に分け、Python のコードを生成して Docker の中で実行し、
Critic が判定し、成功した関数を Skill として保存する。MineDojo/Voyager の型を地理の分析に移したもの。読んだ文書: README、`docs/reference/pipeline.md`、
ADR 0003・0008・0009、研究のまとめ (`2026-10-10_research_summary.md`)、ハーネスの理解の確かめ、自由な探索の記録。

ハーネスとして効いている要素:

| 要素 | 中身 |
|---|---|
| **決定的な検査** | LLM の出力をモデルを使わずに検査する 8 種 (Intent に API の詳細を書かない、対象は ID で 1 つ、既定値で欠落を隠さない、値をコードに貼り込まない、など)。拒否したら理由を添えて作り直させ、尽きたら**失敗を見える形で残す (成功を装わない)** |
| **oracle と、評価用の Goal の取り置き** | 正解を独立に持つ (自前の Overpass・GeoSPARQL、study-geoai の README の数字)。直すのに使った Goal で効果を測らない (ADR 0009、Harness Learning の考え方) |
| **Critic の 2 段** | step の Critic と最終の Critic。両方とも甘すぎ・厳しすぎの例を記録し、再生 (保存した入力で聞き直す) で確かめる |
| **資産の分け方** | 与えられたもの (Dataset Graph、How-to Graph) と獲得したもの (World Graph = 出所つきの発見、Skill library = 確かめたやり方、Exploration Graph = 過程) |
| **文書の分け方** | reference (今の仕様) / ADR (決定) / reports (日付つき、**後から書き換えない**) / evidence (生の記録をコミット) |
| **測り方の反省** | 「judge が最後の観測だけを見て 15/22 と誤報告 → 12/22 に訂正」「2 つ直すとどちらが効いたか分からない」「trace を見て直すとその Goal に合わせ込む」「契約を締めると別の失敗が生まれる」 |
| **ハーネスの理解の確かめ** | 直す前に、モデルがハーネスをどう理解しているかを質問で確かめた (理解していなかった点を説明に足すと答えが変わった。振る舞いが変わるかは別) |

## 2. この作業で、ハーネスが分析の質を上げた場面

この会話の分析で、質が段差で上がった場面を振り返ると、どれも**物差しか検査か外部の正解 (oracle) を足した**時だった。

| 場面 | 足したもの | 何が変わったか |
|---|---|---|
| 単年度の概況 (D20) | 天気予報の物差し (平年・傾向・偶然のぶれ・多重比較のしきい値) | 「最多は〜」の自明な文と、情報のある「予想外」が分かれた |
| 道の契約との突き合わせ (D25) | 外部の oracle (入札監視委員会の契約件数) | 令和6年度の倍増と令和4年度の上川が「推定」から「確認」に変わった |
| 補正予算 (D26) | 外部の oracle (補正予算) | 「年ごとの増減は合わない」を修正 (相関 +0.31 → +0.70。D35 の分類の修正の後は +0.32 → +0.68) |
| 都道府県単位の比較 (D28) | 比べる単位を細かくした物差し | 「冬の空白は固有」を否定し、「7 月への集中が固有」に絞れた |
| 年度ごとの型 (D32) | Y1〜Y6 の固定の型 | 令和5年度の新しい事業の型を見つけ、令和6年度の要確認を年度をまたいで解いた |

逆に、誤りが入ったのは**検査のない層**だった。素案の数字の誤り (D16)、範囲の誤り (term)、平年の値の取り違え (令和4年度)、伊達市の 16 件を砂防と書いた推定
(令和5年度)。どれも、本文に書いた数や推定で、スクリプトの根拠表を通っていない。

**その場の試し (2026-10-13):** 年度ごとの概況 7 本の本文の数字 368 個のうち、45 個 (12%) は根拠表のどこにも出てこない
(会話の中でその場で問い合わせて照合した数、足し算した割合など)。照合はしたが、再現できない数である。Geo-Voyager の言葉でいえば、
**決定的な検査を通らない出力**がこれだけある。

→ 仮説は、この作業の経過と整合する (後から選んだ場面で、対照はない)。分析の質は、モデルの賢さより、物差し・検査・oracle をどれだけ持っているかで決まっていた。

## 3. 参考になる点 (提案、優先順)

### 3.1 本文の数字の決定的な検査 (すぐできる、効果が大きい)

`scripts/check_numbers.py`: 概況の本文の数字が、根拠表 (tables.md) にあるかを検査する。根拠表にない数は、(a) 根拠表に足す、(b) 本文に
「計算: 56% + 30%」のように出どころを書く、のどちらかにしないと通らない。年度ごとの概況を書くたびに走らせる。Geo-Voyager の「拒否して理由を添えて作り直す、
尽きたら失敗を見える形で残す」をそのまま当てはめられる。

### 3.2 発見の台帳 (World Graph に当たるもの)

今は発見が 15 本のレポートと DECISIONS に散らばり、「後のレポートで修正された主張」の表だけが状態を持つ。発見を 1 行 1 件で持つ台帳
(`reports/findings.csv`: 番号、主張、状態 = 推定・確認・否定、根拠の表と行、確かめた oracle、関係する年度、置き換えた発見) にすると、
令和5年度が令和6年度の要確認を解いたような、年度をまたぐつながりを機械的にたどれる。要確認の一覧も、この台帳の「推定」の行から作れる。

### 3.3 取り置きの評価 (合わせ込みを防ぐ)

分類規則 (ねらい・段階・受益・都市計画の定義) は、読み合わせで見つけた誤りを直しながら育ててきた。Geo-Voyager の ADR 0009 と同じく、
**直すのに使わない抜き取り**を年度ごとに取り置き、規則の正しさをそこで測る (例: 各年度 20 件の無作為抽出を固定し、規則を変えるたびに一致率を出す)。
今は「不明 0 件」だけを検査していて、正しさは測っていない。

### 3.4 Critic を分ける

今は私が書き、私が照合し、最後に hfu が読む。Geo-Voyager は step の Critic と最終の Critic を分け、それぞれの誤りを記録している。
ここでも、書いた本人とは別の文脈で「根拠表と本文だけを読み、主張ごとに支持・不支持を付ける」照合を挟める (別のエージェントを使う場合は hfu の了承のうえで)。
最終の Critic である hfu のレビューは、そのあとに置く。

### 3.5 共通部品の整理 (Skill library に当たるもの)

年度の名前、しきい値、計画機関の区分、千人未満の 4 村のコード、都市計画の定義などが、スクリプトの間で写し書きか `exec` による借用になっている。
千人未満の 4 村のコードを一度取り違えたのは、この写し書きによる。`scripts/lib/` に名前付きの関数として置き、単体テストで固定する
(Geo-Voyager は LLM・HTTP・Docker を mock にした単体テストを 800 件以上持つ)。

### 3.6 そのまま取り入れないほうがよい点

- **レポートを書き換えない運用**: Geo-Voyager の reports は日付つきで書き換えない。こちらは古いレポートに「追記 (D 番号)」を入れ、修正の一覧に残す運用で、
  読み手 (hfu) が 1 本で最新の結論を読めることを優先している。来歴は DECISIONS と git に残るので、今の運用のままでよい。
- **細かい段取りの分割**: 文脈の短いモデルのための分割 (Intent ごと、step の上限 8) は、この作業には要らない。こちらに要るのは分割より検査と記憶。
- **自動の curriculum**: Geo-Voyager は、問いを自由に立てさせると「識別子の合計」のような意味のない問いが出た。こちらは hfu が問いを立て、
  「自明か情報か」で問いの価値を測っている。年度ごとの型の Y1 (予想外) と要確認の一覧が、curriculum の役を果たしている。

## 4. まとめ

- Geo-Voyager の設計の中心は、**モデルの出力を信じず、決定的な検査と oracle で確かめ、失敗を隠さずに残す**こと。hfu の「信じるのではなく検証」と同じ考え方を、
  コードとして組み込んでいる。
- この作業でも、分析の質が上がった場面は、物差し・検査・oracle を足した場面と重なり、誤りが入ったのは検査のない層だった。仮説と整合する (同じ書き手が後から選んだ場面で、対照はない)。
- 次に足すハーネスとして、本文の数字の検査 (3.1) と発見の台帳 (3.2) を提案する。どちらも年度ごとの概況の残り (平成30〜21年度) を書く前に入れると効く。

## 追記 (2026-10-13): 入れた後の検証で分かったこと (D34・D35)

- 本文の数字の検査を全レポートに広げると、規則の修正で古くなった数 (相関 +0.70)、手で書き込んだ表の古い値 (stepping)、範囲の誤り (term の 30〜45 日)、
  計算と合わない但し書き (term の「30 日を含む」) が見つかった。どれも、検査を入れる前の照合では見逃していた。
- 全スクリプトを流し直すだけで、規約 (未分類 0 件) と実態 (47 件) の食い違いと、計画機関の分類の誤り (開発局の略記) が見つかった。
- 検査そのものにも穴があった (1 未満の小数を数えていなかった)。ハーネスも検査の対象にする必要がある。
- 拾えない誤りは残る: 数が別の項目に偶然あると通る。平成30年度の「続く空白 7 (正しくは 8)」は、手の照合で見つけた。
